# 门禁裁决响应指南

> “世界上怕就怕‘认真’二字，共产党就最讲认真。”——《在全国宣传工作会议上的讲话》

在响应 `PASS`、`WARN` 或 `BLOCK` 前，先读取命令输出和当前项目策略。数据与直觉冲突时，修改判断，不修改事实。

## 退出码：事实与裁决怎么带回来

退出码是 Agent 与门禁之间的机器可读接口。**`0` 不等于健康，`3` 不等于改动有问题**：

| 退出码 | 含义 |
|--------|------|
| `0` | 已声明策略未触发（`PASS`），或命令正常完成。**不等于 clean**：report-only 指标、finding、`PARTIAL`/`UNAVAILABLE` 明细仍可能在输出里 |
| `1` | 有事实待解释：已声明策略 `WARN`、配置审计 `drift`、`review`/`diff` 找到待调查事实（`review` 的治理复盘不可用也返回 `1`） |
| `2` | 已声明策略 `BLOCK`（强制约束），或测试策略裁决为 `BLOCK` |
| `3` | **事实不可用或配置/环境错误**（`UNAVAILABLE` 与错误均 fail-closed 到 `3`）：baseline 缺失、分析范围或语言形状身份不兼容、配置不可用、用法错误、解析/IO/schema 失败 |

- `openarch check` 的退出码是各处裁决的**合并**（取最强：`3 > 2 > 1 > 0`）：gate 裁决 + 配置审计（`drift` → `1`；未初始化只提示 → `0`）+ 显式 `protected_paths` + `--tests` 时的测试治理。
- 同一个 `3` 既可能是“baseline 需要重建”，也可能是“配置写错了”，下一步完全不同：**先读输出里的 `Verdict:` / `Status:` / `原因:` / `Diagnostic:`，再决定动作**。

## `UNCONFIGURED`

架构策略没有声明 `rules_warn`/`rules_block` 时，`PASS` 只是“没有已声明策略被触发”。若 baseline 当前且有 P95/Top-3，Agent 应运行 `openarch review`，发起一次探索性校准并请项目所有者选择最小 WARN、两条独立 WARN 或记录暂缓理由。不得复制别的项目阈值，也不得在首轮自动 BLOCK。

## `PASS`

`PASS` 只表示已声明策略未触发。它不证明项目健康，也不证明未配置的规则、未支持的 provider 或 `UNAVAILABLE` 范围已经被覆盖。

## `WARN`

`WARN` 不是必须执行的整改指令：它只表示一条已声明策略被触发，是否整改由项目所有者决定。

1. 确认触发规则、文件、实测值和证据状态，并确认它来自哪个 `structural_policies` 总体的 `mode`：报告中的 `enforce` 表示该策略会产出裁决，`observe` 总体不产出裁决。
2. 区分门禁事实、增量诊断和仅供解释的信号；任何单一指标都不能单独等同于腐化。
3. 在修复、记录接受决定（`docs record`）、经配置审计重新校准三条路径中选择一条，并说明理由与回访条件。不得为了通过而降低阈值、改动分类或删除证据。

## `BLOCK`

Agent 不得绕过 `BLOCK`。修复实际违规；若项目所有者明确变更策略，先记录理由并完成配置审计。随后重新运行与改动相称的语言验证和 `openarch check --staged --report`，报告结果。
