# Agent 工作流路由

本页把外部 Agent prompt/skill 的可复用经验落到 OpenArch 的使用路由中。它是行动合同，不是新的 CLI 状态机，也不替用户决定任务顺序。

> 本页是 `SKILL.md` “最小闭环”在“何时执行哪个命令”上的专项展开；整体流程仍以最小闭环为唯一权威。子 Agent 并行条件与主 Agent 责任以 `SKILL.md` “协作与环境”为权威，本页只补充路由和输出合同。

> “没有调查，没有发言权。”——《反对本本主义》

## 路由原则

每次行动都要有五个边界：

1. **对象与事实边界**：实际对象的身份、事实生产者、scope、生命周期与当前观察快照；名称、报告和相邻层测试不自动等同于它。
2. **触发事实**：为什么现在需要这个动作，以及事实来自哪个命令、文件或 provider。
3. **主要动作**：只选择一个最小的 OpenArch 命令或调查动作，不把所有命令串成固定流程。
4. **观察结果**：读取命令输出中的 verdict、coverage、finding、evidence 和 `UNAVAILABLE/PARTIAL`。
5. **停止条件**：什么时候本轮调查已足够，什么时候必须转为修复、用户选择或更小的局部调查。

`PASS` 只表示已声明策略没有触发；没有策略、证据不完整或 provider 不可用都不能解释为 clean。

先以 `openarch context` 获得项目的初始事实投影，再按下表选择一个最能降低不确定性的行动；路由只承接这条认知链，不增加 CLI 状态机。

## 最小路由表

| 当前事实 | 主要动作 | 观察与停止条件 |
|---|---|---|
| 配置或治理状态未知 | `openarch context` | 先补齐事实投影；缺 config 才 `init`，缺 baseline 才 `scan`。状态已清楚后停止，不自动推进后续操作。 |
| baseline 当前且架构策略 `UNCONFIGURED` | `openarch review` | 不把 PASS 当作健康结论；用 P95/Top-3 发起一次探索性校准，请项目所有者选择试行一条 WARN、两条独立 WARN，或暂缓并记录理由。首轮不自动 BLOCK。 |
| 工作树有未暂存改动 | `openarch check --worktree --report` | 先看 I_push、D_MR、证据来源和待处理证据；语义证据不足时记录未知，不把兜底路径当成完整语义。 |
| Git index 已暂存、准备提交 | `openarch check --staged --report` | 只以 index 快照裁决；缺语义证据时按文件真实变更类型调查或补证据，不预先放宽门禁。 |
| 反复修改同一模块，或需要解释存量风险 | `openarch review` / `review --evolution` | 只把 Top 负担、历史共同变化和 finding 当调查线索；确认具体模式后才建立脚本或项目合同。 |
| 已有可复现的静态腐化假设 | `openarch rules facts` → 选择 skeleton → `rules check` → `rules scan` | 先保存正例或历史 revision，再回扫合法、违规和不可用样本；零命中是治理后的 `CLEAN`，不是未经验证的覆盖证明。 |
| 测试框架或收集边界不确定 | `openarch check --tests` 或 `review` | 区分工具覆盖度与策略裁决；`UNAVAILABLE/PARTIAL` 只限制测试治理，不阻断生产代码调查。 |
| 无 diff 上下文但需要全量裁决（冷检出、CI 验证） | `openarch check --full [--tests]` | 跳过 diff 前置，一次完成门禁 + 配置审计 + 测试治理；仍按全量信号面逐项消费，不因全量输出而跳过 WARN/finding。 |
| 能力、脚本或经验文档发生实质变化 | `openarch docs status` / `docs check --changed <path>` | 只更新当前项目 DocumentStore；产品 Skill、runtime 镜像和发行资产由产品仓库维护。 |

路由表不是强制顺序。一次行动若同时满足多行，先选能减少最大不确定性的那一行，并在摘要中说明为何不执行其他动作。

## Agent 摘要合同

每轮调查或修复后，用以下结构向用户报告：

```text
事实：已执行的命令、实际输出、证据来源与范围
推断：基于事实的解释、置信度、反例
建议：下一步动作、前提、预计改变的边界
未知：UNAVAILABLE/PARTIAL、未验证的语义与剩余风险
停止条件：本轮何时结束，何时需要用户决定或继续调查
```

不要把推断写成 finding，把建议写成 gate，也不要用“已处理”替代可复现的验证命令。

## 用户选择与子 Agent

只有在持久化模式、共享文档范围、策略提升、不可逆修改或外部副作用会改变结果时，才向用户提问：

- 一个互斥维度用宿主原生单选；多个互不依赖的防线族用多选。
- 选项应说明影响和证据缺口；例行 `scan/check` 不制造选择题。
- 宿主没有原生选择能力时，才退回简短的编号选项，不把问题埋在长段落中。
- 首次策略校准也是用户选择：报告观察到的 P95/Top-3 和证据范围，让用户选择最小 WARN 试行、两条独立 WARN 试行或暂缓；Agent 不得默默保持未配置，也不得替用户写入阈值。

只有独立证据源、不会修改同一文件/状态且不依赖彼此结论的问题，才适合委派子 Agent。每个子 Agent 只回答一个问题，并返回证据、反例、未知、范围和可复现命令；主 Agent 负责比较冲突、修改共享状态和最终验证。

## 经验闭环

同一腐化模式再次出现时，先把稳定不变量固化为当前项目的脚本、合同或测试，再扫描和修复存量；依赖设计意图、运行时语义或昂贵全程序分析的模式，记录为项目经验并引导调查，不伪造静态规则。经验属于当前项目，不回写安装版 Skill。
