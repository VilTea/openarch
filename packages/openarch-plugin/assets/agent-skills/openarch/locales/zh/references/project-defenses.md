# 项目防线

> “我们的任务是过河，但是没有桥或没有船就不能过。”——《关心群众生活，注意工作方法》

在选择默认资产、建立项目防线、提升 finding，或解释测试、安全、反模式覆盖前阅读本页。

## 以证据选择资产

默认脚本、模板和 provider 是可选参考，不是隐式策略。根据当前 `languages`、架构事实、已有 provider 与团队意图选择最小集合。`openarch rules facts` 只展示兼容模板族；推荐不等于已安装、已校准或可进入门禁。

用 `openarch init --install-script <id>` 安装指定可复用资产。保留已有项目脚本；仅当确认目标未被定制且资产合同过期时使用 `--replace-script <id>`。路径、层权重、authority 范围和阈值只能来自受治理项目，不能复制其他项目未经校准的数值。配置变化用 `check --record-config` 审计。

## 持久防腐

防腐不是一次扫描全绿，而是主动防御的长期工作。每次变更都会带来新的不确定性；不要在所有信号上分散力量，也不要因暂时无法自动分析而放弃。围绕当前最有证据、最影响协作或变更可靠性的模式，完成一个最小闭环后再扩展：调查事实与边界，建立可验证防线，回扫存量，修复或校准，验证并沉淀经验。人、Agent、脚本、测试和协作文档共同构成这条防线；任何一方的未知都应如实保留。

### 启发式探索与协作

复杂问题先按可验证的问题拆分，而不是按目录、角色或猜测的解决方案拆分。一个问题若有独立的证据源、不会修改同一文件或状态、也不依赖另一项调查的结论，宿主支持子 Agent 时可以并行调查。每个子 Agent 必须交付证据、反例、未知、受影响范围和可复现命令；主 Agent 负责比较结论、处理冲突并运行最终验证。

共享架构判断、同一根因的多种症状、需要顺序建立的事实，以及会触碰同一状态的工作，不适合并行。并行只扩大观察面，不能替代问题界定、规则校准或最终责任。

### Agent 输出合同

反模式或架构调查的 prompt 只提供路由，不制造未经验证的状态机。Agent 的行动摘要应分开写：事实（来源与命令）、推断（置信度与反例）、建议（前提与下一步）以及未知/`UNAVAILABLE`。需要用户决定持久化、共享范围或策略提升时，使用宿主原生单选/多选；例行检查不伪装成选择。每个阶段给出可复现命令和停止条件，完成“调查 → 防线 → 回扫 → 修复/校准 → 验证/记录”后再扩展范围。

### 建立最小防线

对于可复现的腐化模式：

1. 保存修复前观察；若仓库已干净，保存真实历史 revision 或 fixture。
2. 编写最小项目规则，明确违规、合法替代和 `UNAVAILABLE` fixture；遵守 [script-authoring.md](./script-authoring.md)。
3. 运行 `rules check`，再用 `rules scan` 或 `rules discover` 回扫当前范围。
4. 修复 finding 或记录合理边界；零命中是 `CLEAN`，不是失败。
5. 只有正例、fixture 与当前干净回扫都存在时，才能在项目策略中提升到 `warn` 或 `block`；被选中的规则 `UNAVAILABLE` 时应关闭失败。

不得为设计意图、运行时行为、广泛数据流、业务语义、并发、授权、`CVE` 或 `SCA` 伪造静态规则。结构信号只排序调查优先级，之后仍需代码、历史、合同、外部扫描器和测试。

## 测试与安全边界

测试 provider 产生框架事实；项目策略决定 finding 严重性和豁免。`AVAILABLE`、`PARTIAL`、`UNAVAILABLE`、`NOT_CONFIGURED` 与策略 `PASS` 相互独立。未知框架、自定义 runner 或不完整收集保持局部状态，生产治理仍可继续。

直接 API 误用或明确静态不变量可以成为仅报告的语言或项目规则。污点、密钥、`CVE`、类型或数据流、竞态和业务授权需要外部 provider 或聚焦的人类调查；这些 finding 都不进入 `CRL` 或 `I_push`。
